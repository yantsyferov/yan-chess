- [x] **Slice 12: Post-verify bug fixes (session reconnect on refresh + home auto-restore in new tab)**

  Two bugs discovered during a live two-player session that the automated e2e suite missed because it drives sockets inline, never through a browser refresh or a new tab. Both behaviours are already prescribed by the existing functional-spec (§2.5 reconnect, §2.6 two-tab sync); this slice is implementation only — no spec change.

  **Bug A — Timer appears to "reset" on page refresh.** The in-memory Zustand store loses state on reload; `useOnlineGameStore` restarts at `INITIAL_STATE` with zero clocks. The server-side `hello → game.snapshot` path exists but doesn't fire because `getSocket()` memoises the Socket.IO instance with the access-token value captured at first call — on refresh that is `null` (access token is in-memory, cleared by reload). The socket connects unauthenticated, the server disconnects it, `hello` never resolves to a snapshot, and the UI stays at the empty-store defaults (looks like a reset timer).

  **Bug B — New tab lands on login/guest home instead of the active game.** `Home.tsx` reads `useAuthStore.user` directly; a new tab's Zustand store is empty, so the guest branch renders. No `fetchMe()` runs on Home, so a valid refresh cookie is never consumed into a session, and the player sees `/login` CTAs instead of their ongoing game. `ProtectedRoute` would restore the session on `/play` — but §2.6 implies that even landing on `/` of a new tab mid-game should route to the current game, not to the guest landing.

Alternatively (cleaner): on each `getSocket()` invocation, read the latest token from `useAuthStore.getState().accessToken`; if the memoised socket's `auth.token` differs, disconnect and rebuild. Pick the lighter path — the behaviour is: after `fetchMe` resolves on refresh, the socket must reconnect with the new access token so `hello` succeeds and the server emits `game.snapshot`. **[Agent: react-frontend]**
